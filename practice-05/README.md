## Эксперимент с циклом событий

До запуска исходного `event-loop.js` прогноз: **A → B → C → D → E → F**. Фактический вывод совпал. После добавления собственного `Promise.resolve().then(...)` с меткой G прогноз до повторного запуска: **A → B → C → D → G → E → F**. Повторный запуск подтвердил этот порядок.

| Метки | Причина |
|---|---|
| A, B, C | Синхронный код, включая часть `async`-функции до `await`. |
| D, G, E | Продолжения Promise и `await` в очереди микрозадач; они выполняются в порядке постановки. |
| F | Таймер `setTimeout(..., 0)` попадает в следующую очередь задач и ждёт завершения синхронного кода и микрозадач. |

Если удалить обработчик G, исчезнет только его метка, а исходный порядок A–F восстановится. Если удалить обработчик D, G выполнится перед E. Сам `await null` всё равно переносит продолжение на микрозадачу.

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовый локальный HTTP API, маршруты, фильтры и ошибки; не изменялся. |
| `src/api-client.js` | Сборка URL, GET/JSON, тайм-аут, отмена и классификация ошибок. |
| `src/task-api.js` | Маршруты задач и категорий, проверка фильтров и структуры ответов. |
| `src/variant.js` | Конфигурация варианта 6: `{ categoryId: 2 }`. |
| `src/main.js` | Общий и индивидуальный консольные сценарии. |
| `src/partial-load.js` | Дополнительная независимая загрузка через `Promise.allSettled`. |

`fetchFn` передаётся в фабрику для проверки клиента без сети. Ответы 400/404/503 проверяются по статусу отдельно: `fetch` при них не отклоняет Promise. После разбора JSON доменный модуль дополнительно проверяет поля задачи, категории и коллекции, поскольку корректный синтаксис JSON не гарантирует корректные данные.

## Общий JSON-клиент

| Требование | Реализация и проверка |
|---|---|
| `baseUrl` | Абсолютный HTTP(S) без query/hash; завершающие `/` нормализуются. Проверки клиента 01 и 04. |
| Query | `URLSearchParams` кодирует `&`, кириллицу и пробелы; `false` и `0` сохраняются, пустые значения пропускаются, объект не меняется. Проверки 02–03 и собственная. |
| `Accept` | У каждого GET `Accept: application/json`. Проверка 05. |
| HTTP-статус | При `!response.ok` создаётся `ApiError` вида `http`, статус важнее ошибочного тела. Проверки 08–09. |
| `Content-Type` | У успешного ответа должен быть JSON, кроме 204. Проверки 07 и 10. |
| JSON | Успешный JSON возвращается, повреждённый даёт `invalid-response`. Проверки 06 и 11. |
| Тайм-аут | `AbortSignal.timeout`, `kind: "timeout"`. Проверка 14. |
| Внешняя отмена | `AbortSignal.any` объединяет сигналы, явная отмена даёт `aborted`. Проверка 15. |

| Сценарий | Запуск 1 | Запуск 2 | Запуск 3 | Наблюдение |
|---|---:|---:|---:|---|

## Отладка

Точки останова для показа: перед `fetchFn` в `src/api-client.js`, сразу после получения `Response`, перед `response.json()` и в ветке `catch`. Успешный запрос `/tasks?completed=false&priority=high`: `status = 200`, `ok = true`, JSON Content-Type, payload с тремя задачами и `meta.total = 3`, ошибка отсутствует. Ошибочный запрос `/tasks/999`: `status = 404`, `ok = false`, JSON Content-Type, payload `{ error: { code: "TASK_NOT_FOUND", message: "Задача с id 999 не найдена.", details: { id: 999 } } }`; итоговый `ApiError` имеет `kind = "http"`, `status = 404` и тот же код. Эти значения получены при выполнении запросов к API.

## Дополнительное задание А

`loadPartialData(api, filters)` в `src/partial-load.js` запускает запросы задач и категорий вместе через `Promise.allSettled`. Результат содержит `tasks`, `categories`, `meta` и `errors`: при отказе одной части её данные становятся `null`, а успешная часть сохраняется. Ошибка описывается полями `kind`, `message`, `status`. Четыре собственные проверки подтвердили успех обоих запросов, ошибку только задач, только категорий и обе ошибки. Основной контракт `loadInitialData` сохранён.
